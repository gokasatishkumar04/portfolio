Tab One

Overview & Architecture

What CLARITY does, in plain language and in technical language, followed by the three design principles that run through the entire codebase and the end-to-end pipeline a single document triple travels through.

In Plain Terms

A smart triage layer sitting in front of a manual document review queue

Picture a mid-size operation receiving roughly 1,500 Purchase Order, Shipment, and Invoice bundles every week. Without CLARITY, every single bundle takes the same manual review path, whether it is flawless or full of mismatches. CLARITY reads each bundle, compares the three documents against each other and against how that client and vendor have historically behaved, and assigns a grade — GOOD, MEDIUM, or BAD.

That grade decides how much of a reviewer's time the bundle actually deserves: GOOD sets move straight through, MEDIUM sets get a light, AI-explained check, and BAD sets go to full manual review without ever touching the generative-AI layer at all.

In Technical Terms

A dual-engine scoring layer feeding a fixed-threshold router and a grounded RAG explainer

PDF triples are extracted with pdfplumber into structured JSON, then converted into a feature vector scored independently by a deterministic Rules Engine and a scikit-learn RandomForestClassifier. A Decision Engine converts the model's readiness probability into a grade against two fixed thresholds.

GOOD and MEDIUM sets are explained through a FAISS-based retrieval step and a LangChain-orchestrated Gemini prompt grounded in current and historical evidence. BAD sets bypass generative inference entirely. Every result persists to SQLite behind a seven-page Streamlit dashboard that contains no business logic of its own.

Three Principles, Enforced by an Automated Test Suite

What keeps the deterministic and probabilistic halves of the system honest

  • Deterministic and probabilistic reasoning stay strictly separate: the Rules Engine never consults the model's probability, and a rules failure never silently overwrites the model's grade — a set that fails several rules can still be graded GOOD, with the failures shown alongside it rather than suppressing it.
  • No component fabricates a result when a dependency is unavailable: FAISS, LangChain, and the Gemini API each raise an explicit error rather than degrading to a fake fallback, so a missing dependency is loud, not silently wrong.
  • Historical features are computed only from data available at scoring time: client- and vendor-level statistics used to featurize any split are built strictly from data preceding it in time, which rules out target leakage from a document's own outcome into its own prediction.

Data & Feature Engineering

In the absence of real client data, CLARITY generates its own historical corpus and verifies the PDF round trip end to end, then converts every document set into a compact, leakage-free numeric vector.

Synthetic Corpus

5,000

Document sets generated across five synthetic clients, each assigned one of five behavioral profiles — strong, quantity_issues, amount_issues, delay_issues, moderate — configurable toward 20,000–50,000 for production scale.

Class Balance

42.5 / 42.6 / 14.9

Percent split across GOOD, MEDIUM, and BAD respectively, produced by an explicit scoring function of quantity mismatch, amount mismatch, delay, currency mismatch, and missing fields.

PDF Round Trip

Verified

A subset of generated sets is rendered into real PDFs from ground-truth values, then parsed back with pdfplumber; only the structured JSON — never raw PDF text — feeds feature engineering.

Six Feature Groups, One Flat Vector Per Document Set

#Feature GroupWhat It Captures
01 Document Completeness Whether mandatory fields across the PO, Shipment, and Invoice are present and valid before any cross-document comparison is even attempted.
02 PO ↔ Shipment Consistency Quantity mismatch between what was ordered and what shipped, and shipment delay relative to the agreed schedule.
03 PO ↔ Invoice Consistency Quantity mismatch, unit-price and invoice-amount variance, and currency mismatch between the order and what was billed.
04 Cross-Document Signals Aggregate mismatch count plus quantity- and amount-consistency scores computed across all three documents together — the single strongest predictive signal in the system.
05 Client Historical Behavior Pre-aggregated statistics on how a given client's document sets have graded historically, looked up by client ID rather than encoded directly.
06 Vendor Historical Failure Rate The vendor's historical rate of failed or flagged sets, giving the model a prior on vendor reliability without ever seeing a raw vendor identifier. Design rule: high-cardinality identifiers like PO numbers are never one-hot or label encoded — only used as lookup keys into these pre-aggregated tables.
01

Client and vendor historical features are themselves derived from outcomes — a natural leakage vector

Risk If a client's historical GOOD/BAD rate is computed using data that includes the very document being scored, the model effectively sees its own answer before predicting it.
Safeguard The historical-statistics tables used to featurize any split are built strictly from data preceding it in time, and the feature matrix never includes the label or its underlying quality score — properties directly asserted by automated tests, not left to code review alone.
02

High-cardinality identifiers threaten to blow up the feature space and hurt generalization

Risk PO numbers and similar identifiers are effectively unique per document — one-hot or label encoding them directly would make the model memorize individual documents instead of learning generalizable patterns.
Safeguard Identifiers are used only as lookup keys into pre-aggregated historical statistics, keeping the feature space compact and generalizable across clients and vendors the model has never scored before.

Tab Three

Rules Engine & Random Forest

Two independent scoring paths run on the same structured record — one deterministic, one probabilistic — and neither is allowed to silently override the other.

Deterministic Path

Rules Engine

Checks mandatory fields, PO-to-Shipment and PO-to-Invoice quantity mismatches against a 2% tolerance, invoice-amount and currency mismatches, invalid dates, duplicate identifiers, mismatched PO references, and shipment delay severity, aggregating failures into an overall pass/fail result.

This output is surfaced to the reviewer and to Gemini but never silently overrides the model's grade — failures are shown alongside the grade, not used to suppress it.

Probabilistic Path

Random Forest Readiness Model

A single scikit-learn RandomForestClassifier — 300 trees, maximum depth 12, balanced-subsample class weighting, fixed random seed — trained on the engineered feature vector.

The dataset is split chronologically 70/15/15 into train, validation, and test partitions rather than shuffled, mirroring production use: scoring documents that arrive after everything the model was trained on. The GOOD-class probability is used directly as the continuous readiness score.

Tab Four

Decision Engine & Grounded Explanation

Pure routing logic converts a probability into a grade and an action; only GOOD and MEDIUM sets ever reach retrieval or generation.

Fixed-Threshold Grading — r(x) = P(GOOD | x)

grade(x) = GOOD  if r(x) ≥ 0.80

         = MEDIUM if 0.50 ≤ r(x) < 0.80

         = BAD   otherwise

These thresholds are deliberately global constants rather than per-client parameters — client-specific behavior is instead absorbed into the model through the historical features covered in Tab Two, so clients with different baseline risk profiles are compared on a genuinely equivalent scale.

Semantic Retrieval

FAISS, With Hard Client Isolation

Historical sets are embedded offline with a TF-IDF vectorizer followed by a Truncated SVD projection into a fixed 256-dimensional dense space, fit once and reused — never refit — at query time. Vectors are L2-normalized so the FAISS IndexFlatIP inner-product search is equivalent to cosine similarity.

A search over-fetches, then discards any result whose client ID doesn't match the querying set — one client's history can never leak into another's explanation. Retrieval supplies context only; grading remains the Random Forest's responsibility alone.

Prompt Orchestration

LangChain → Gemini, Grounded and Bounded

For every GOOD or MEDIUM set, the current record, rules result, model grade and top features, client historical stats, and FAISS-retrieved context are assembled into a LangChain PromptTemplate. Gemini is instructed to use only supplied evidence, never invent facts, and respond with a fixed seven-field JSON schema — summary, key findings, anomalies, historical comparison, risk factors, recommendation, confidence.

04

Gemini's model API returned a deprecation error mid-project

Incident The gemini-1.5-flash model the integration was calling was retired mid-project, surfacing as an HTTP 404 the failure-handling layer had to name specifically rather than mask.
Response Fixed by reconfiguring to gemini-3.6-flash. A missing key, network failure, or malformed response is never papered over with a fabricated summary — the service returns a structured "unavailable" result with a plain-English reason the dashboard displays verbatim; 401/403 names key rejection, 429 uses fixed wording noting deterministic results remain available, with no aggressive retry.

Tab Five

Results, Validation & Operational Hardening

Governance-critical behaviors are enforced by an automated test suite, and the operational discipline that keeps LLM usage bounded proved as consequential as the modeling choices themselves.

Automated Test Suite

29 / 31

Tests passed in the development sandbox; 2 skipped cleanly because they require the real faiss package, unavailable offline — no test failed. Coverage spans rule evaluation, no-leakage feature engineering, the PDF round trip, chronological-split training, decision routing, FAISS client isolation, and Gemini response handling.

Presentation Layer Discipline

7 pages

The Streamlit dashboard is reached through a single navigation selector rather than st.tabs(), because Streamlit re-executes every tab's code on every rerun — a selector paired with one render function per page ensures only the viewed page does any work, or triggers a Gemini call.

Persistence

SQLite, upsert

Every processed set is keyed by document-set ID with upsert semantics preserving an in-progress reviewer's status across reprocessing; a set with a successful Gemini response is never re-submitted to Gemini on a later pass.

Most Consequential Operational Fix

The historical-bootstrap batch job was silently exhausting the Gemini quota on every fresh startup

Prior to hardening, every fresh startup of the dashboard's first-run historical bootstrap silently issued hundreds of Gemini calls while seeding history — exactly the quota-exhausting behavior a constrained LLM integration cannot tolerate.

The fix: the bootstrap job now runs the deterministic path only, passed an explicit flag guaranteeing it never calls FAISS or Gemini, for any grade. Only the live document-upload flow — going through the same process_document_set() entry point — is eligible for retrieval and generation.

Tab Six

Limitations, Future Work & Conclusion

Built under a small, fixed technology mandate and a network-isolated sandbox, with the honest boundaries of the prototype stated alongside its results.

01
Sandbox Constraint

The live Gemini path, real faiss / langchain-core, and Streamlit itself could not be exercised end to end in the development environment

The prototype was developed in a network-isolated sandbox. Every dependent code path still raises an explicit error rather than a fake fallback when a dependency is unavailable, so the boundary of what was and wasn't live-tested is never hidden from the reviewer.

02
Corpus Scale

The default 5,000-document synthetic corpus is smaller than the 20,000–50,000-record production scale in the original specification

Chosen for fast iterative development and adjustable via a single configuration value — scaling up is a config change, not a redesign.

03
Future Work

Exercising the live Gemini and FAISS paths in a networked environment, and evaluating threshold sensitivity

Beyond the two fixed cut points (0.80 / 0.50) currently used for grading, future iterations could study how routing outcomes shift as those thresholds move.

Conclusion

Classical ML makes the governance-critical decision; generative AI only explains it

CLARITY demonstrates that a document pre-governance layer can combine a single, well-evaluated classical machine-learning model with retrieval-grounded generative explanation without blurring the boundary between the two. A deterministic Rules Engine and a Random Forest classifier make the governance-critical decisions; a FAISS-plus-Gemini pipeline only explains those decisions for the sets a human reviewer will need to interpret, never touching sets already flagged unready.

The classifier avoids the single worst error a governance system can make — passing an unready document set through as ready — and the engineering discipline required to keep LLM usage bounded in an interactive dashboard proved as consequential to the system's practicality as the modeling choices themselves.
